## Executive Summary

The notice states that Splunk released fixes for vulnerabilities in supported
Splunk releases and that successful exploitation could allow elevated
privileges on an affected host. It reports no known associated exploits or
DoD-related incidents at the time of the supplied notice. Those statements
must not be treated as proof of the current exploit situation.

The individual public CVE records describe differing conditions and impacts,
including denial of service, authorization failures, and command execution
under the Splunk service account. Applicability and required privileges vary
by CVE; consult the current vendor details rather than assuming every listed
issue has the same impact.

## Vulnerable Applications/Systems and Countermeasures

### Vulnerable Applications/Systems with Fixes Available

The supplied notice identifies Splunk Enterprise versions prior to `10.4.4`,
`10.2.8`, `10.0.11`, and `9.4.16`. Splunk's product-level tables identify
these affected maintenance branches and first fixed releases:

| Splunk Enterprise branch | Vendor-listed affected versions | First fixed version on that branch |
| --- | --- | --- |
| 10.4 | 10.4.0-10.4.3 | `10.4.4` |
| 10.2 | 10.2.0-10.2.7 | `10.2.8` |
| 10.0 | 10.0.0-10.0.10 | `10.0.11` |
| 9.4 | 9.4.0-9.4.15 | `9.4.16` |

These are aggregate product tables, not a claim that every CVE affects every
listed version. Other branches, unsupported versions, and other Splunk products
require separate vendor review; do not infer their status from this table.

### Fix Action

The notice directs administrators to upgrade to a non-vulnerable Splunk
Enterprise version. Select the applicable fixed version or a later
vendor-supported release, confirm the supported upgrade path, and follow the
current vendor guidance for each applicable CVE.

**Additional vendor actions:** SVD-2026-1007 says `CVE-2026-76292` and
`CVE-2026-76295` also require a Splunk Secure Gateway upgrade to `3.10.12`,
`3.9.26`, or `3.8.73`, or later on the applicable supported branch. Verify the
deployed app version and product compatibility; an Enterprise upgrade alone
is not sufficient to claim those CVEs are remediated.

For `CVE-2026-76290`, the vendor's CVE-specific description directs customers
to prepare existing Edge Processor instances, enable package-download
authentication, and restart after upgrading. The separate Edge Processor
guide calls the setting optional and warns that enabling it before preparing
every existing instance can interrupt ingestion. If Edge Processor is in scope,
resolve the applicable requirement with the vendor and system owner, and
follow the current, release-specific preparation guidance before any change.
Do not assume the lab has this optional feature.

### Note

The supplied notice specifies these Splunk Enterprise upgrade targets:
`10.4.4` or later, `10.2.8` or later, `10.0.11` or later, and `9.4.16` or
later. A later release or cross-branch upgrade still requires vendor support
and compatibility review; version numbering alone does not establish an
approved upgrade path.

The notice states that administrators unable to implement the required
remediation must have a documented, AO-approved CDR Override. It also states
that supersession does not remove the vendor-remediation requirement, grant
additional time, or make an unremediated notice compliant; the current vendor
remediation must be applied for compliance. Confirm these requirements and
any current notice revision with the organization's authorized IAVM and
approval authorities.

## Lab assessment and remediation workflow

1. Confirm the current notice, scope, timeline, and any changes with the
   authorized IAVM owner. Reconcile the CVE-list discrepancy above.
2. On the authorized `RHEL-SPLUNK01` lab system, identify the installed
   Enterprise version and build. For the `/opt/splunk` installation and
   `splunk` service account documented in [Step 14](../../steps/14-transfer-and-install-splunk-enterprise.md),
   a version-only check is:

   ```sh
   sudo -u splunk /opt/splunk/bin/splunk -version
   ```

   Expected result: a Splunk version and build. If the path or account differs,
   confirm the actual installation with the administrator; a missing command is
   not proof the system is unaffected. Record approved, sanitized information
   in [installed versions](../../reference/versions.md) and keep detailed evidence private.
3. Privately inventory the enabled Secure Gateway and Edge Processor components,
   if present. Compare each product, branch, version, and applicable feature
   with the current CVE-specific vendor guidance. The Windows Universal
   Forwarder is a separate product and needs its own applicability review.
4. Obtain change approval; verify compatible OS, apps, upgrade path, package
   integrity, maintenance window, and private, recoverable backups. Follow
   Splunk's instructions for the actual release and installation method. Do
   not overwrite an existing installation merely by following the initial
   installation procedure.
5. Perform the approved upgrade and any applicable component-specific actions.
   Verify the version and relevant functionality afterward, review ingest
   health, and record the evidence and exceptions in the authorized system.
   Do not mark the notice compliant solely because a package version changed.
6. Submit required acknowledgments or reports through the appropriate IAVM
   process. Keep raw scan output, private identifiers, approvals, and backups
   out of GitHub. The [sanitized validation template](../../../evidence/sanitized/iavm-2026-a-1195-validation.md)
   remains pending until actual work is observed and approved for publication.

**Command overview:** `sudo -u splunk` runs the version query as the documented
service account; `splunk -version` reports the installed version and build.
The command does not install a patch or submit a report.
