## Prioritized intelligence and applicability

### 1 Current week Linux persistence reporting

Microsoft's [GSocket investigation](https://www.microsoft.com/en-us/security/blog/2026/11/11/global-socket-how-threat-actors-weaponizing-gsocket-stealthy-c2/), published **November 11**, describes multiple Linux intrusions in which remote access survived remediation of the original application vulnerability. Observed behavior included outbound relay connections and layered persistence. This report covers multiple actors; it does not establish a single APT attribution. The analyzed telemetry includes activity from March through August 2026.

**Apply to the lab:** review available Linux execution and persistence evidence on exposed services. The shipped Linux lab-log input does not provide full process telemetry. **Immediate mitigation:** isolate a credibly compromised host and restrict unnecessary egress under authority. **Prevention:** minimize application exposure and validate process, service and outbound monitoring. **Owner/verification:** Linux and network leads must show that unauthorized access and persistence are addressed; a patched application alone is insufficient. Review the complete source for product-specific recommendations.

### 2 Current week exposed credential abuse

Microsoft's [exposed-secrets investigation](https://www.microsoft.com/en-us/security/blog/2026/11/05/threat-actors-use-agentic-ai-tooling-to-find-and-abuse-exposed-secrets/), published **November 5**, describes agent-assisted discovery of authentication material in public repositories and subsequent cloud abuse. Its observations include activity beginning in August and service-principal sign-ins from October 28. Do not infer that every actor using the same framework is state-sponsored.

**Apply to this public repository:** inspect proposed publication for secrets and investigate any actual exposure privately. **Immediate mitigation:** revoke/rotate exposed material and investigate its use; deleting a committed string does not revoke access. **Prevention:** secret scanning, publication review, least privilege and supported short-lived workload authentication. **Owner/verification:** repository and cloud owners verify old authentication fails and dependent services use clean access. The lab's IdM logs do not substitute for cloud audit records.

### 3 SlippyNunchucks application delivery carryover context

[ESET's November 4 report](https://www.welivesecurity.com/en/eset-research/slippynunchucks-hijacks-sogou-input-methods-brand-promotion-mechanism-to-distribute-malware/) describes a China-aligned actor abusing Sogou Input Method's insecure HTTP configuration delivery through DNS hijacking to deploy DarkVigil. ESET observed the Sogou-linked activity from **July 1, 2026** and reports Tencent addressed the issue in **version 16.10 on October 30**. The point of DNS manipulation remained unresolved; the report does not establish which router or provider performed it.

**Applicability:** first inventory whether this software is installed; its presence is not established for WINHUNT01. **Mitigation:** suspend suspect delivery paths, preserve artifacts and investigate unexpected execution. **Prevention:** apply the publisher's supported update and review software provenance and DNS trust. **Owner/verification:** endpoint/software owners verify installed publisher/build and configuration, then inspect for pre-update compromise. Updating the application does not prove existing malware was removed.

### 4 BITTER PapRAT carryover context

[FortiGuard Labs' November 2 investigation](https://www.fortinet.com/blog/threat-research/bitter-expands-its-arsenal-with-paprat) attributes a Windows campaign targeting South Asian organizations to BITTER with high confidence. It describes activity over preceding months, including shortcut/disk-image/installer chains, scheduled tasks and PapRAT. Treat this as the vendor's attribution rather than proof that an equivalent lab event belongs to BITTER.

**Applicability:** Windows process and task behaviors can be reviewed on WINHUNT01 with verified Sysmon and Security collection. **Mitigation:** isolate a corroborated affected endpoint, preserve artifacts and examine persistence and exposed credentials. **Prevention:** approved software execution, cautious handling of unsolicited shortcuts/installers and behavior monitoring. **Owner/verification:** endpoint and detection leads verify task/process context against change records and clean baselines; file names alone do not establish compromise.

### Detection prerequisites and bounded searches

1. Confirm the authorized host/source inventory, UTC interval, retention, permissions, ingestion delay and extraction using **Q0** in the [query and validation pack](HUNT_QUERIES.md).
2. Verify Windows EventCode/EventID, Image, CommandLine, User and ProcessGuid are populated. Confirm Security audit policy produces task records. The shipped Sysmon configuration limits network/file/registry coverage.
3. Confirm whether Linux events are synthetic lab records or actual process/audit/application telemetry. Record the gap if only the lab log is available. Optional cloud, appliance and network data need separately approved collection.
4. Start with these two read-only searches; use the pack's Q2 through Q6 for persistence, task registration, installer context and scoped timeline pivots.

Linux name candidates:

```spl
index=linux earliest=-7d latest=now
| regex _raw="(?i)(gs-netcat|gsnetcat|gsocket)"
| table _time host source sourcetype _raw
| sort 0 _time
```

Windows scheduled-task command candidates:

```spl
index=sysmon earliest=-7d latest=now (EventCode=1 OR EventID=1)
| eval image=lower(coalesce(Image,process_path,"")), cmd=coalesce(CommandLine,process_command_line,"")
| where like(image,"%schtasks.exe") AND (match(lower(cmd),"/create") OR match(lower(cmd),"/change"))
| table _time host User ProcessGuid ParentImage image cmd
| sort 0 _time
```

5. Run the pack's harmless `makeresults` matching/nonmatching controls before interpreting filter behavior. Expected results are four PASS rows for the Linux filter and two PASS rows for the task-command filter. These controls do not execute software, generate source events or validate forwarding/alerts. Results are **pending live Splunk execution**.
6. Inspect raw candidates privately. Correlate actual execution, file/task/service definitions, identity and network activity. Compare to changes and known-good configuration; retain competing explanations.
7. If suspicious, expand to the earliest plausible compromise period, including older campaign dates above, within actual retention and authority. Save UTC bounds, query version, evidence IDs and warnings. Missing fields or zero results leave a coverage question; they do not prove absence.
8. Route credible compromise using the phases and severity below. Record a supported, benign, inconclusive or escalated disposition with a named next owner.

## 1 Detection

1. **SOC analyst:** open a private incident/hunt record with discovery time, source, affected service, report/query version and evidence reference.
2. Verify source generation, extraction, time alignment, retention and asset identity; run Q0 and document telemetry gaps.
3. Execute the bounded candidate searches and harmless filter controls; preserve search warnings and actual results privately.
4. Correlate process/task/service/identity/network observations and check authorized administration or exercises with the owner.
5. Assign provisional severity and page the proper lead immediately if P1/P2 is credible. Missing evidence does not justify delaying response to ongoing harm.
6. **Exit:** an evidence-supported benign disposition or a reproducible candidate with owner, severity, next action and review time.

## 2 Detection and Analysis Identification

1. **IC, hunter and forensic lead:** document malicious and benign hypotheses, confidence, UTC timeline and evidence references.
2. Scope hosts, privileged users, application identities, reachable secrets, services, data and possible downstream tenants. Expand the time window when plausible compromise predates seven days.
3. Acquire volatile/persistent evidence using trusted approved methods; retain originals, working copies, hashes, collector/tool/time and transfers. Record emergency changes that affect evidence.
4. Check exact product/build, effective fixes and exposure history against current vendor guidance. Classify a vulnerability separately from observed exploitation.
5. Correlate authentication, execution, persistence, access and data movement independently. Engage legal/privacy if sensitive data may be involved; do not equate successful sign-in with exfiltration.
6. Declare/update the incident and select containment targets, authority, dependencies, validation and rollback. **Exit:** accepted response ownership, scoped findings/unknowns and an actionable containment plan.

## 3 Containment

1. **IC directs technical leads:** confirm exact affected hosts, identities, application trust and routes; check business/safety dependencies and delegated authority.
2. Isolate a credibly compromised host or withdraw/restrict an exposed service as approved; retain management and forensic access. Do not wait for a lengthy export when harm is active.
3. Restrict affected identity/app access and coordinate provider-supported session/token actions; issued tokens may require separate invalidation or expiry handling.
4. For an unpatched suspected zero-day, apply validated vendor-supported workarounds or reduce exposure/disable the vulnerable function, with an owner and expiry.
5. Independently verify unwanted access fails and required response paths work; inspect alternate footholds, segments and dependent identities. Escalate containment failure immediately.
6. **Exit:** harmful paths interrupted with evidence, residual routes documented and longer-term containment owned. Remain contained if verification fails.

## 4 Eradication

1. **Forensics and technical leads:** preserve selected artifacts, then establish the removal or clean-rebuild plan; use trusted media when privileged or base-system trust is lost.
2. Review and address redundant persistence: tasks/services, cron/startup, web components, unauthorized keys, credentials/grants and third-party connections as applicable.
3. Apply the exact supported product fix or maintain the tested temporary control. Patching an entry point does not remove an established foothold.
4. Rotate exposed and reachable downstream authentication material from a trusted system, in dependency order; remove unauthorized methods, owners, roles and trust.
5. Re-run scoped hunts and independent forensic/configuration checks. Verify the old access fails and business dependencies have clean credentials.
6. **Exit:** the IC and service owner accept evidence of trust restoration, foothold removal and entry-path remediation; unresolved uncertainty remains restricted and owned.

## 5 Recovery

1. **Recovery lead and owner:** choose verified clean images/backups predating the earliest plausible compromise; protect the last clean copy and record recovery objectives.
2. Restore in a segmented environment using clean management access, patches, least privilege and approved configuration.
3. Validate service function, data integrity, identity dependencies, backups, agent/forwarder health, source-to-index collection and alert routing.
4. Recheck the previous access/persistence paths safely, review current vendor reconnection instructions for affected integrations and obtain IC/owner approval.
5. Reconnect in stages under heightened monitoring. Proposed starting point: continuous alerting and daily review for seven days, extended for criticality, dwell time and gaps. Re-isolate on recurrent persistence, unexpected privilege, suspicious access or missing critical telemetry.
6. **Exit:** service acceptance, security evidence, residual-risk owner and monitoring handoff are documented. Quiet logs alone do not prove recovery.

## 6 Post Incident Activity Lessons Learned

1. **IC:** convene technical, owner, legal/privacy and business participants; proposed target is within five business days of stabilization.
2. Reconstruct discovery, acknowledgment, effective containment and accepted restoration times; record where assumptions or visibility failed.
3. Complete the evidence-linked incident report, impact and data assessment, decision history, vendor cases and approved notification receipts.
4. Assign remediation, detection and prevention tasks with owner, due date, measurable acceptance and retest. Review whether the primary/backup escalation path worked.
5. Test improvements with harmless matching and nonmatching controls under approved lab scope; distinguish source, forwarding, query and alert outcomes.
6. **Exit:** owner-approved closeout, retained evidence/legal hold, accepted open tasks and a proposed 30-day action review. Reopen when material new evidence changes the conclusion.
